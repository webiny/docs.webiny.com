## Development

### Standalone Hosting: Run Webiny Without AWS ([#5454](https://github.com/webiny/webiny-js/pull/5454))
{/* REVIEW-PENDING @adrians5j — confirm this entry, then delete this line */}

Webiny has a new hosting type, standalone, that runs the API and Admin on a single long-running Node server backed by a SQL database. It needs no AWS account and no Pulumi. Choose it when creating a project, or pass it in non-interactive mode:

```
npx create-webiny-project my-project --hosting-type standalone
```

<Alert type="info">

Standalone hosting is in alpha and is marked as such in the project setup prompt.

</Alert>

- **SQLite or PostgreSQL.** Pick the database when creating the project. The driver is set in `webiny.config.tsx` with `<Infra.Sqlite>` or `<Infra.Postgres>`, and the build leaves out the driver you don't use.
- **One command for local development.** `yarn dev` starts the API and Admin and serves both on one URL. The port comes from the `PORT` environment variable, or the first free port from 3001.
- **Deployable builds.** `webiny build` produces a self-contained `build/` folder with the server entry point, worker files and a pruned `node_modules`, ready to copy to any server. Example GitHub Actions workflows, a Dockerfile and an nginx config are in [`docs/gh-actions-workflows/standalone`](https://github.com/webiny/webiny-js/tree/next/docs/gh-actions-workflows/standalone).
- **The same features as on AWS.** Background tasks, scheduled actions, real-time notifications over WebSockets and streamed HTTP responses all run on the standalone server.
- **Built-in sign-in.** Users sign in with an email and password configured through `<SelfHostedAuth />`. A forgotten password can be reset with a code sent by email, or by an administrator with `yarn webiny reset-password <email>`.
- **Licensing without the CLI.** A deployed server reads the license from the `WEBINY_PROJECT_ID` and `WEBINY_PROJECT_API_KEY` environment variables.

New projects run without a `.env` file and ship a `.env.example` that lists the variables you can override.

### Remote Components Feature Flag ([#5559](https://github.com/webiny/webiny-js/pull/5559))
{/* REVIEW-PENDING @Pavel910 — confirm this entry, then delete this line */}

Remote Components is a new enterprise feature that allows you to create, edit, and bundle React components directly from the Admin UI, then load and render them in a Next.js frontend at runtime. The feature includes a Monaco editor with live sandbox preview, AI-powered component generation, and a Next.js runtime loader.

The `remoteComponents` feature flag gates the entire extension. When disabled, no GraphQL schema is registered and no admin UI is mounted.

### EventBridge Scheduler Update Fix ([#6002](https://github.com/webiny/webiny-js/pull/6002))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

The EventBridge scheduler's `update()` didn't create the schedule when it was missing, so rescheduling failed once the schedule was deleted. It now creates the schedule if needed.

### GraphQL Schema Cached Across Requests ([#5830](https://github.com/webiny/webiny-js/pull/5830))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

The executable GraphQL schema is now cached and reused across requests when the schema factories produce identical output. The cache keys on type definitions plus resolver/decorator paths, and tenants with the same models share one cached entry.

Warm request times dropped from ~88ms to ~75ms locally, with `GraphQLEngine.execute` going from ~19ms to ~2ms per request. Heap allocation per request dropped from ~15MB to ~5MB.

### Faster CLI Startup ([#5765](https://github.com/webiny/webiny-js/pull/5765), [#5773](https://github.com/webiny/webiny-js/pull/5773), [#5779](https://github.com/webiny/webiny-js/pull/5779), [#5781](https://github.com/webiny/webiny-js/pull/5781), [#5790](https://github.com/webiny/webiny-js/pull/5790), [#5811](https://github.com/webiny/webiny-js/pull/5811))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

The CLI loaded unnecessary code on every command, even `webiny --help`. Pulumi, AWS SDK, GraphQL libraries, and other heavy dependencies now load only when the command actually needs them. The WCP environment lookup also uses a cached REST endpoint instead of GraphQL, saving a network round trip on most commands. Combined, these changes reduce `webiny --help` startup time from ~2.5s to ~1.3s.

### Faster Watch Mode Startup ([#5781](https://github.com/webiny/webiny-js/pull/5781), [#5786](https://github.com/webiny/webiny-js/pull/5786))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

`webiny watch` sat silent for about 17 seconds before serving anything, spending most of that time determining whether extensions use default or named exports. This now uses a syntax-based check instead of invoking the TypeScript type checker, reducing startup from ~26s to ~12s. Additionally, watch processes now stop properly when the CLI exits via SIGTERM, preventing orphaned build workers that caused `Cannot find module` errors on subsequent runs.

### Project License Now Applied Before Configuration Renders ([#5775](https://github.com/webiny/webiny-js/pull/5775))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

The project configuration was rendered before the WCP license was fetched, causing license-gated extensions to be silently excluded. Extensions like `tenant-manager` and `languages` that depend on license entitlements are now correctly included in the configuration after the license is known.

### `webiny info` Lists All Deployed Environments ([#5810](https://github.com/webiny/webiny-js/pull/5810))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

Running `webiny info` without `--env` should list all deployed environments, but it only showed `dev`. The `--env` option defaulted to `"dev"` even when omitted, preventing the command from discovering other environments. It now lists all deployed environments when no environment is specified.

### Bug Reporter ([#5736](https://github.com/webiny/webiny-js/pull/5736), [#5746](https://github.com/webiny/webiny-js/pull/5746))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

A built-in bug reporter is now available in every project. Press `Cmd+Shift+B` (or `Ctrl+Shift+B`), describe the issue, optionally paste a screenshot, and submit. The report includes environment information and a timeline of recent actions (route changes, clicks, GraphQL operations, errors) to help diagnose issues.

Two modes are available:

- **Compose mode** (default): Opens GitHub with the report pre-filled. You create the issue yourself.
- **Filed mode**: When configured with a GitHub token, the API creates the issue directly, including uploading screenshots.

The timeline records the last 150 events in memory. It captures labels and selectors for clicks, never field values—reports can be filed from tenants with real customer data.

An optional AI drafting extension in `extensions/bugReportAi` can improve the report using AI before submission. It integrates with AI Powerups settings like any other capability.

### CLI Startup Performance Improvements ([#5752](https://github.com/webiny/webiny-js/pull/5752), [#5755](https://github.com/webiny/webiny-js/pull/5755))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

CLI startup is now significantly faster:

- **Preflight checks optimized**: The system requirements and package version checks that run before every command were spawning multiple processes. Node and npm versions are now read from the environment, and the package version check caches its result against the lockfile hash. Together these save about 1.4 seconds.
- **Config rendering moved in-process**: The project config was rendered in a forked child process with a full DOM environment. It now renders in the CLI's own process using a minimal React renderer. This saves about 2 seconds and makes error messages much more useful—stack traces now point to the actual location in `webiny.config.tsx`.

```bash
# Before: ~4 seconds
# After: ~2 seconds
yarn webiny --help
```

### Lazy Route Matching Reduces Cold Start Cost ([#5668](https://github.com/webiny/webiny-js/pull/5668))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

Matching an incoming request used to construct every registered HTTP route — including the GraphQL engine, all CMS schemas, and the AI provider — just to read their paths and find a match. A simple OPTIONS preflight paid for the entire dependency graph and then threw it away.

Routes are now split into lightweight definitions (method, path) and their handlers. The router matches on definitions and only constructs the handler for the matched route. This noticeably reduces cold start time for requests that hit simpler endpoints.

### Background Task Definitions Split Into Metadata and Handler ([#5684](https://github.com/webiny/webiny-js/pull/5684), [#5692](https://github.com/webiny/webiny-js/pull/5692), [#5699](https://github.com/webiny/webiny-js/pull/5699), [#5709](https://github.com/webiny/webiny-js/pull/5709), [#5710](https://github.com/webiny/webiny-js/pull/5710), [#5711](https://github.com/webiny/webiny-js/pull/5711))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

Looking up a background task by ID previously built all 24 registered task definitions—including their dependencies like CMS contexts and OpenSearch clients—even though only one task was needed. Task definitions are now split into two parts:

- **`TaskDefinition`** carries only metadata (id, title, maxIterations, etc.) and has no dependencies
- **`TaskHandler`** contains `run()` and lifecycle hooks, built only when that specific task executes

This eliminates unnecessary dependency construction during task lookups. The `run()` method and all lifecycle hooks (`onBeforeTrigger`, `onDone`, `onError`, `onAbort`, `onMaxIterations`) now receive the task definition as a parameter, allowing decorators to branch on task properties without hardcoding task IDs.

```typescript
import { TaskDefinition, TaskHandler } from "webiny/api";

class MyTaskHandler implements TaskHandler.Interface<MyInput, MyOutput> {
    constructor(private readonly cmsContext: CmsContext.Interface) {}

    async run({ input, definition }: TaskHandler.RunParams<MyInput>) {
        if (definition.maxIterations > 100) {
            // Handle long-running task differently
        }
        // ...
    }
}

export const MyTaskHandlerImpl = TaskHandler.createImplementation({
    implementation: MyTaskHandler,
    dependencies: [CmsContext]
});

class MyTask implements TaskDefinition.Interface<MyInput, MyOutput> {
    id = "myTask";
    title = "My Task";
    handler = MyTaskHandlerImpl;
}
```

### HTTP Routes Now Have Names and Support Handler Decoration ([#5673](https://github.com/webiny/webiny-js/pull/5673))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

HTTP routes now carry a `name` property, and `request.route` provides the matched route's metadata (`name`, `method`, `path`) inside handlers. This enables route-specific decoration using standard DI decorators:

```typescript
import { HttpRouteHandler } from "webiny/api";

export default HttpRouteHandler.createDecorator({
    decorator: class implements HttpRouteHandler.Interface {
        constructor(private decoratee: HttpRouteHandler.Interface) {}

        async handle(request: HttpRouteHandler.Request, response: HttpRouteHandler.Response) {
            if (request.route.name === "my-route-get") {
                if (request.headers["x-api-key"] !== "expected") {
                    return response.status(401).json({ message: "Not authorized." });
                }
            }
            return this.decoratee.handle(request, response);
        }
    },
    dependencies: []
});
```

Omit the name check to wrap all routes—useful for logging or timing middleware.

### AI SDK Tools Split Into Definition and Handler ([#5706](https://github.com/webiny/webiny-js/pull/5706))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

AI SDK tools followed the same pattern as background tasks: looking up available tools built all 11 tool instances and their dependencies, even though `getToolSet()` only reads metadata like `name`, `description`, and `inputSchema`.

Tools are now split into `AiSdkToolDefinition` (metadata only, no dependencies) and `AiSdkToolHandler` (the `execute` method and its dependencies). Handlers are built only when the AI model actually calls that specific tool during a conversation.

<Alert type="info">

The `AiSdkTool` export has been replaced by `AiSdkToolDefinition`. Tools must now specify a `handler` class—inline `execute` methods are no longer supported.

</Alert>

The CMS storage layer was restructured for better maintainability. ### Platform-Agnostic Search Index Tasks ([#5487](https://github.com/webiny/webiny-js/pull/5487), [#5450](https://github.com/webiny/webiny-js/pull/5450), [#5431](https://github.com/webiny/webiny-js/pull/5431))

### Postgres Storage Operations Research and Design ([#5402](https://github.com/webiny/webiny-js/pull/5402))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

This release includes internal research and design documentation for adding Postgres + OpenSearch storage operations to the Headless CMS. No code changes are included — this is foundational work exploring a hybrid architecture where Postgres serves as the source of truth for writes and point lookups, while OpenSearch handles all search, filter, and sort operations.

Key architectural decisions documented:

- Table-per-model structure with shared tables using a tenant column
- System fields stored as real columns, user field values in a single `values` JSONB column
- WAL logical replication for Postgres → OpenSearch synchronisation
- Upsert pattern for CRUD operations

<Alert type="info">

This is research-only — no production code or migration paths are included in this release.

</Alert>

### SQL Storage Now Supports Multi-Tenancy ([#5812](https://github.com/webiny/webiny-js/pull/5812))
> ⏳ REVIEW-PENDING `@brunozoric`: confirm this entry, then delete this line.

The SQL CMS storage (`@webiny/api-headless-cms-sql`) previously used single-column primary keys, which meant the same model, group or entry ID could not exist in multiple tenants. All keys now include the tenant, and every query is scoped accordingly. This also fixes several cross-tenant data leaks where operations could inadvertently read or modify another tenant's records.

<Alert type="info">

No migration is provided. If you are using the unreleased SQL storage in development, drop and recreate your database.

</Alert>

### Birthday Picker for Date Fields ([#6033](https://github.com/webiny/webiny-js/pull/6033))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

Date-only fields now support a step-by-step **Birthday Picker** renderer. The field displays as a `DD / MM / YYYY` bar; clicking it opens a card that walks through day, month, and year grids with the newest year first.

### Model Providers Replace Synchronous Resolution Hooks ([#5632](https://github.com/webiny/webiny-js/pull/5632), [#5633](https://github.com/webiny/webiny-js/pull/5633), [#5634](https://github.com/webiny/webiny-js/pull/5634), [#5636](https://github.com/webiny/webiny-js/pull/5636), [#5638](https://github.com/webiny/webiny-js/pull/5638), [#5639](https://github.com/webiny/webiny-js/pull/5639), [#5645](https://github.com/webiny/webiny-js/pull/5645), [#5650](https://github.com/webiny/webiny-js/pull/5650), [#5651](https://github.com/webiny/webiny-js/pull/5651), [#5654](https://github.com/webiny/webiny-js/pull/5654))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

A significant internal refactor removes the `RequestContextInitializer` hook system that previously ran after authentication to inject pre-resolved CMS models and other request-scoped values into the dependency container. The hook existed because DI resolution is synchronous while model loading is async — so a hook deposited the resolved value for later consumers.

That pattern forced every route to pay for model resolution whether it needed those models or not, and it created ordering constraints between hooks that were documented in comments but enforced only by convention.

The new approach uses **providers** — lightweight wrappers that defer the async work until a consumer actually needs the value:

```typescript
class SomeRepository {
  constructor(private pageModelProvider: PageModelProvider.Interface) {}

  async execute() {
    const pageModel = await this.pageModelProvider.get();
    // ...
  }
}
```

This affects `FileModel`, `FolderModel`, `AcoFolderModel`, and all four Website Builder models (Redirect, Variant, Experiment, Page). The scheduler service and the sharp image transform handler follow the same pattern.

<Alert type="info">

If you were injecting any of these model abstractions directly (e.g., `FileModel`, `PageModel`), you now need to inject the corresponding provider and call `.get()` inside your async method.

</Alert>

## Breaking Changes

### Feature Flags Replace WCP as Primary Feature Availability System ([#5559](https://github.com/webiny/webiny-js/pull/5559))
{/* REVIEW-PENDING @Pavel910 — confirm this entry, then delete this line */}

Feature flags are now the primary authority for feature availability, replacing the previous WCP-based system. The license acts as the gate, while configuration in `webiny.config.tsx` acts as the switch within that gate. In the Admin UI, `useFeatureFlags()` replaces `useWcp()`, and `FeatureFlag.CanUse*` components replace `Wcp.CanUse*` components.

The decision flow is:
1. No license → feature disabled
2. License blocks the flag → feature disabled (config ignored)
3. License allows + config explicitly false → feature disabled
4. License allows + config unset → feature enabled (license is authority)
5. Not license-governed + license exists → config decides

Use the new `isEnabled("name")` API with dot-path support for checking feature availability:

```typescript
import { useFeatureFlags } from "webiny/admin";

const { isEnabled } = useFeatureFlags();

// Check if a feature is enabled
if (isEnabled("aiPowerups.cms.entryGeneration")) {
  // Feature is available
}
```

### HTTP Response Streaming on Lambda and Self-Hosted ([#5622](https://github.com/webiny/webiny-js/pull/5622))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

Routes can now return an `HttpStreamBody` to deliver HTTP responses incrementally. On self-hosted Node the chunks arrive as the source produces them. On AWS the API uses a Lambda Function URL with response streaming, fronted by CloudFront.

```typescript
import { HttpStreamBody } from "webiny/event-handler";

async function* generate() {
    yield "data: first\n\n";
    await delay(100);
    yield "data: second\n\n";
}

return response.status(200).type("text/event-stream").send(new HttpStreamBody(generate()));
```

Transports that cannot stream call `collect()` and return the whole body at once, so existing routes are unaffected.

<Alert type="info">

CloudFront compression buffers chunks and defeats incremental delivery, so the `/stream/*` behavior disables it. The origin read timeout is raised to 60 seconds — it applies to the gap between packets, not the total stream duration.

</Alert>

### Express-Style Response Builder for HTTP Routes ([#5611](https://github.com/webiny/webiny-js/pull/5611))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

HTTP routes now receive a mutable response builder as a second argument, making it easier to set headers, cookies, and status codes:

```typescript
async handle(request: IHttpRequest, response: IHttpResponseBuilder) {
    return response
        .status(201)
        .cookie("sid", token, { httpOnly: true, secure: true, sameSite: "lax", maxAge: 3600 })
        .json({ id });
}
```

Routes that return a plain `IHttpResponse` object continue to work unchanged. The new `cookie()` method is the only way to emit multiple `Set-Cookie` headers, which the old `headers: Record<string, string>` could not express.

### HTTP Response Compression ([#5612](https://github.com/webiny/webiny-js/pull/5612))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

HTTP responses are now compressed automatically when the client accepts it. The transport negotiates `accept-encoding`, preferring Brotli over gzip, and skips bodies under 1 KB or already-binary content. This restores the compression that was lost when we moved off Fastify and prevents large GraphQL responses from hitting the API Gateway size limit.

### Injectable `StringFormatter` and `Slugify` Features ([#5549](https://github.com/webiny/webiny-js/pull/5549))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

New `StringFormatter` and `Slugify` features are now available in both `@webiny/app-admin` (frontend) and `@webiny/api-core` (backend), providing injectable, decoratable string formatting. This lets you customise slug generation across your project by decorating a single feature rather than hunting down individual usages.

```typescript
import { Slugify } from "webiny/api-core";

const MySlugify = Slugify.createDecorator(() => {
    return {
        execute: value => {
            return value.trim().toLowerCase().replace(/\s+/g, "_");
        }
    };
});

container.registerDecorator(MySlugify);
```

A backend `DateFormatter` feature is also included for deterministic UTC date/time formatting.

## AI Power-Ups

### Per-Capability AI Model Resolution ([#5691](https://github.com/webiny/webiny-js/pull/5691))
> ⏳ REVIEW-PENDING `@adrians5j`: confirm this entry, then delete this line.

AI features previously used whatever model happened to be first in the providers list. This has been replaced with a three-layer configuration:

- **Connections** — credentials for a vendor, carrying no model. Using two models from the same vendor no longer requires duplicating the API key.

Existing projects keep working without changes — `standard` is seeded from your existing provider configuration.
