## Website Builder

### Fixed Missing `version` and `metadata` Fields in Single-Page Queries ([#5727](https://github.com/webiny/webiny-js/pull/5727))
{/* REVIEW-PENDING @Pavel910 — confirm this entry, then delete this line */}

The `GET_PAGE_BY_ID` and `GET_PAGE_BY_PATH` queries in the Website Builder SDK were missing the `version` and `metadata` fields from their selection sets. If you needed these fields, you had to patch the SDK manually. Both fields are now included by default.

### Fixed Stale Page Revision Data After Mutations ([#5757](https://github.com/webiny/webiny-js/pull/5757))
{/* REVIEW-PENDING @Pavel910 — confirm this entry, then delete this line */}

Creating, publishing, unpublishing, or deleting page revisions did not update the revisions cache, so the editor's revisions drawer and top bar dropdown displayed stale data until a page reload. All revision mutations now properly update the cache, and both UI components are driven from a shared `RevisionListPresenter` instead of local state copies.

### Added Delete Revision API Endpoint ([#5757](https://github.com/webiny/webiny-js/pull/5757))
{/* REVIEW-PENDING @Pavel910 — confirm this entry, then delete this line */}

The admin app called `websiteBuilder.deletePageRevision`, but the mutation was never declared on the backend — the entire client feature was wired to a non-existent endpoint. The mutation now exists and delegates to the CMS `DeleteEntryRevisionUseCase`, which handles deleting the latest revision and cascading to a full entry delete when necessary.

### Improved Revision List Actions and Confirmations ([#5757](https://github.com/webiny/webiny-js/pull/5757))
{/* REVIEW-PENDING @Pavel910 — confirm this entry, then delete this line */}

Per-revision actions (create from, edit, publish, unpublish, delete) are now determined by the presenter rather than derived in the view. Destructive actions now require confirmation through a dialog and display a toast with the outcome. Previously, delete ran on the first click and failed silently on error.

### Fixed Workflow Decorators Not Applying to Top Bar Actions ([#5757](https://github.com/webiny/webiny-js/pull/5757))
{/* REVIEW-PENDING @Pavel910 — confirm this entry, then delete this line */}

The page editor config was not registered through `Plugins`, so workflow decorators were never applied to the top bar actions. Additionally, an approved review no longer counts as "under review", so the editor becomes writable again and offers **Publish** instead of **New Revision**.

### Permission Checks for Scheduled and Folder Publishing ([#6173](https://github.com/webiny/webiny-js/pull/6173), [#6240](https://github.com/webiny/webiny-js/pull/6240))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

Scheduling a page to be published or unpublished now checks the permissions of the caller. When using folder level permissions, publishing, republishing and unpublishing a page requires write access to its folder.

## Development

### Debug Logger Tool ([#5734](https://github.com/webiny/webiny-js/pull/5734))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

A new opt-in, permission-gated debugger is now available for troubleshooting issues in environments where you cannot access AWS or the underlying code. When a user with the `dev-tools.debug` permission enables capture, debug payloads from instrumented call sites are returned in the GraphQL response under `extensions.debug`.

**Key details:**

- Capture is requested per-request via the `x-webiny-debug` header (set to `1`, or a glob pattern like `cms.os.*` with `!` to exclude).
- Debug sessions are buffered in memory (capped at 4 MB), and payloads never reach CloudWatch—only the permitted user sees them.
- The first instrumented call site is `cms.os.list`, which captures OpenSearch query and response data around entry listing.

A new **Dev Tools → Debugger** panel in Admin lets you toggle capture, filter by namespace, and download a JSON report. Collected sessions are held in memory only and do not persist beyond the browser tab.

<Alert type="info">

After deploying this release, you must redeploy your API infrastructure (`yarn webiny deploy api`) and invalidate your CloudFront distribution to ensure the new `x-webiny-debug` header is forwarded correctly. Without this, the feature silently captures nothing.

</Alert>

### Fixed Peer Dependency Ranges Being Locked During Package Publishing ([#5777](https://github.com/webiny/webiny-js/pull/5777))
{/* REVIEW-PENDING @adrians5j — confirm this entry, then delete this line */}

When publishing packages, peer dependencies were incorrectly locked to the exact version installed in the monorepo rather than preserving the original range. This caused installation failures with `@webiny/website-builder-nextjs` — npm would error with `ERESOLVE` if your project used a different Next.js version than the one pinned during publishing.

Peer dependencies are now published with their original version ranges. For example, `@webiny/website-builder-nextjs` now correctly declares `next: >=15.0.0 <16.0.0`, allowing installation alongside any compatible Next.js 15 version.

### Updated Core Dependencies ([#6168](https://github.com/webiny/webiny-js/pull/6168))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

This release upgrades several core dependencies to their latest versions. The upgrade includes internal type fixes required by the new dependency versions — no changes to your project code are required.

### Updated Dependencies ([#6253](https://github.com/webiny/webiny-js/pull/6253))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

Routine minor and patch dependency updates, including `@aws-sdk/*`, `@pulumi/pulumi`, `@opensearch-project/opensearch`, and various build/test tooling.

## Admin

### Fixed Keyboard Shortcut Leak on Component Unmount ([#5757](https://github.com/webiny/webiny-js/pull/5757))
{/* REVIEW-PENDING @Pavel910 — confirm this entry, then delete this line */}

`useHotkeys` leaked registered shortcuts when a component unmounted while shortcuts were active. The cleanup effect closed over stale state, so a drawer that unmounted while open never released its `esc` binding, causing the next component to claim it to throw an error.

### Fixed `getUser` Query When Missing `where` Argument ([#6240](https://github.com/webiny/webiny-js/pull/6240))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

The `getUser` query no longer fails when the `where` argument is omitted. Previously, this would cause an error instead of returning a validation message.

### Scheduler Validates Schedule Date Before Creating Actions ([#6240](https://github.com/webiny/webiny-js/pull/6240))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

Scheduling an action without a valid schedule date now returns a clear invalid date error instead of creating a malformed scheduled action.

### Custom Scheduler Namespaces Require Permission Implementation ([#6240](https://github.com/webiny/webiny-js/pull/6240))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

If you have a custom scheduler namespace, you must now register a `SchedulerPermissions` implementation. Without one, getting, listing and cancelling scheduled actions returns a not authorized error. Additionally, the `namespace_startsWith` filter has been removed from `ListScheduledActionsUseCase` — use `namespace` instead.

### API Keys and Roles Now Require Matching Permissions ([#6268](https://github.com/webiny/webiny-js/pull/6268))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

When creating or updating API keys and roles, the requested permissions are now validated against the permissions of the current identity. You can only grant permissions that you yourself hold (wildcards are taken into account). Attempting to assign permissions beyond your own scope returns a not authorized error. Existing permissions already stored on the API key or role can be kept unchanged.

### Stricter Identity and Request Checks ([#6173](https://github.com/webiny/webiny-js/pull/6173), [#6203](https://github.com/webiny/webiny-js/pull/6203), [#6240](https://github.com/webiny/webiny-js/pull/6240))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

- **Cookie authentication:** the authentication cookie is accepted only for the requests that need it, such as downloading private files.
- **CORS:** stricter CORS headers on API responses.
- **Requests:** stricter JSON parsing and validation of accepted content types.
- **Current user:** `getCurrentUser` checks the identity of the caller.
- **Websockets:** stricter permission checks.
- **Folders:** creating a folder validates the folder `type` first.

## Headless CMS

### Fixed Full-Text Search Failing on Non-Text Fields in OpenSearch ([#5819](https://github.com/webiny/webiny-js/pull/5819))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

Full-text search queries in OpenSearch would fail when searchable JSON fields contained non-text values like dates, numbers, or booleans. The search now uses lenient mode, allowing these mixed-type fields to be searched without errors. Additionally, full-text search paths now correctly include parent object fields, and the `contains` filter in DynamoDB properly searches objects inside arrays.

<Alert type="info">

If you have a custom `CmsEntryOpenSearchFullTextSearch` implementation, ensure you add `lenient: true` to your search configuration.

</Alert>

### Added Model Access Guard for Content Models ([#6240](https://github.com/webiny/webiny-js/pull/6240))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

A new `ModelAccessGuard` provides an additional access rule layer for content models on top of the existing Headless CMS permissions. This allows for more granular control over which identities can access specific models.

### Stricter Access Checks for Entries and Models ([#6173](https://github.com/webiny/webiny-js/pull/6173))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

- **Own entries:** getting entries by ID and listing revisions respect the "own entries only" permission.
- **Private models:** private content models are no longer reachable through `getContentModel` or the generic entry queries.
- **Scheduled publishing and bulk actions:** both check the permissions of the caller.

### Bulk Delete Now Validates Delete Permission Per Entry ([#6240](https://github.com/webiny/webiny-js/pull/6240))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

Bulk delete operations now check the delete permission for each individual entry rather than only validating at the operation level. This ensures folder level permissions and other entry-specific rules are respected.

### Entry Access Checks Use Stored Entry Data ([#6268](https://github.com/webiny/webiny-js/pull/6268))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

Updating an entry and creating a revision from an entry now check access against the stored entry rather than the submitted data. This closes a potential privilege escalation vector where manipulated request payloads could bypass access controls.

### Entry Owner Cannot Be Changed via Updates ([#6268](https://github.com/webiny/webiny-js/pull/6268))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

The `createdBy` value sent when updating an entry or creating a revision from an entry is now ignored. This prevents unauthorized ownership transfers. Setting `createdBy` when initially creating an entry still works as expected.

### Folder Level Permissions Apply to Publishing Operations ([#6240](https://github.com/webiny/webiny-js/pull/6240))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

When using folder level permissions, publishing, republishing and unpublishing an entry now requires write access to its folder. Previously, these operations only checked top-level permissions.

### Tenant and Language Entries Require Matching Permissions ([#6240](https://github.com/webiny/webiny-js/pull/6240))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

Some resources available through the Headless CMS API now require their own permissions:

- **Tenant entries**: A role with Headless CMS permissions but without the Tenant Manager permission can no longer read or change tenant entries through the CMS API.
- **Languages**: A role with Headless CMS permissions but without the Languages permission (with write access) can still read languages, but can no longer create, update or delete them through the CMS API.

### Expired Record Locks Now Properly Released ([#6268](https://github.com/webiny/webiny-js/pull/6268))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

When a record lock expires, it is now taken over by deleting the existing lock record and creating a new one, rather than attempting to update it. This resolves edge cases where stale locks could block legitimate edit attempts. Record locking operations also check permissions more strictly.

## File Manager

### Tenant-Scoped Storage and Stricter Permission Checks ([#6173](https://github.com/webiny/webiny-js/pull/6173), [#6203](https://github.com/webiny/webiny-js/pull/6203))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

- **Uploads:** files, including multi-part uploads, are stored under tenant-scoped storage keys, and the upload input is validated.
- **Private files:** downloading a private file requires an authenticated identity with the permission to read files.
- **Settings:** updating the File Manager settings requires the settings permission, and the settings input is validated more strictly.
- **Performance:** the S3 client is cached and reused.

## Webhooks

### Per-Webhook Signing Secrets ([#6193](https://github.com/webiny/webiny-js/pull/6193))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

Webhook signing secrets can now be configured individually for each webhook, rather than relying on a single global secret. You can set, change, or clear the signing secret via GraphQL, the SDK, or the Admin webhook form. The Admin interface also includes new actions to generate a random secret and copy it to your clipboard. Signing secret validation has been improved, along with fixes to permissions and overall Admin UX for webhook management.

### Webhook Settings Require the Webhook Permission ([#6203](https://github.com/webiny/webiny-js/pull/6203))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

The `getSettings` query returned the webhook settings, including the signing secret, without a permission check. It now requires the permission to manage webhooks, the same as the other webhook operations.

### Stricter Webhook Endpoint Validation ([#6203](https://github.com/webiny/webiny-js/pull/6203), [#6240](https://github.com/webiny/webiny-js/pull/6240))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

Webhook endpoint URLs are validated before they are saved, and the check refuses more forms of local addresses.

### Webhook Redirects Are No Longer Followed ([#6240](https://github.com/webiny/webiny-js/pull/6240))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

When delivering a webhook, redirect responses (3xx) are no longer followed. The redirect response is recorded as the delivery result instead. This change hardens webhook security by preventing potential SSRF attacks through redirect chains.

## Infrastructure

### Fixed GuardDuty Malware Protection Deployment and Destroy Failures ([#6186](https://github.com/webiny/webiny-js/pull/6186))
{/* REVIEW-PENDING @brunozoric — confirm this entry, then delete this line */}

The GuardDuty malware protection plan (used for File Manager threat detection) had missing dependency declarations. This caused two issues:

- **During deployment:** the plan could be created before its IAM policy was attached, leaving it in `ERROR` status.
- **During destroy:** the policy attachment could be removed before the plan, preventing GuardDuty from deleting its EventBridge rule and causing `webiny destroy` to fail with a `BadRequestException`.

The plan now correctly depends on its policy attachment, and the event-forwarding target depends on its role policy.

<Alert type="info">

If your stack is already in a stuck state, you may need to manually clean up the GuardDuty EventBridge rule before `webiny destroy` will succeed.

</Alert>
